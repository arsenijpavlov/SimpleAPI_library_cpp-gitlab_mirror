
Сводный манифест возможностей библиотеки SimpleAPI

Этот документ содержит структурированное описание всех функциональных возможностей библиотеки SimpleAPI. Документ служит единым источником правды для контекста текущих архитектурных обсуждений.

1. Архитектурная философия и стандарты

• Стандарт C++11: Полная автономность кодовой базы без требований к современным стандартам (C++14/17/20/23).
• Максимальная обратная совместимость (Legacy): Железобетонная работоспособность на старых кросс-компиляторах (проверено на GCC 4.9.4) и старых версиях системных библиотек (glibc 2.14) под архитектуры ARM (платформа OCT3500 – Octasic).
• Zero-Dependency (Self-Contained): Библиотека не использует сторонние тяжелые зависимости (вроде Boost, nlohmann/json или protobuf). Весь ключевой функционал написан с нуля.
• Философия открытых примитивов: Библиотека предоставляет высокоуровневые интерфейсы, но оставляет открытыми для разработчика все низкоуровневые примитивы, полезные в обычных проектах и embedded-разработке.
• Иерархия инкапсуляции:
	• simpleapi:: — корневые прикладные классы.
	• simpleapi::utils — публичные прикладные системные утилиты.
	• simpleapi::tools — скрытые технические классы реализации (например, ElementArray), интерфейсы и хардкорный движок метапрограммирования.

2. Динамическая подсистема конфигурации (Класс Config)

Основной интерфейс для гибкой работы с древовидными структурами данных «на лету» (динамический контейнер).
• Управление типами (ValueType): Поддерживает примитивы (long double, bool, std::string, const char*), пустые типы (ValueType::eNull) и структурированные контейнеры (ValueType::eJson, ValueType::eArray).
• Бесшовная интернационализация / Конвертация форматов: Полная рантайм-совместимость и свободная двусторонняя конвертация между JSON и INI внутри одного объекта Config (метод toString()), запланировано добавление в эту парадигму поддержки XML и YAML.
• Отказоустойчивый (Толерантный) парсинг: При возникновении синтаксической ошибки в файле, успешно прочитанные до этого момента ветки данных не уничтожаются. Метод error() сигнализирует о сбое, а getError() возвращает точную строку описания ошибки.

Специфика реализации JSON (RFC 8259):

• Поблажки парсера строк: Допускается отсутствие запятых (перенос строки эквивалентен разделителю). Кавычки для ключей/значений обязательны только в случае, если строка содержит несколько слов.
• Отсутствие принудительной сортировки: Данные сохраняют естественный порядок, автоматическая сортировка ключей отсутствует.

Специфика реализации INI:

• Автовыведение типов: Расширяет стандартный INI. Текстовые значения автоматически распознаются внутренним парсером и приводятся к типам: числа, bool (true/false, +/-), массивы или вложенный JSON.
• Поддержка многострочности: Значение переменной корректно считывается на последующих строках, если не закрыта кавычка, строка оканчивается на \ или следующая строка начинается с пробела/табуляции.
• Склеивание дубликатов в массивы: Одинаковые ключи в рамках одной группы автоматически преобразуются в массив (ValueType::eArray).
• Иерархия через слэш: Поддерживается глубокая вложенность ключей с использованием разделителей / и \. При записи JSON-объекты первого уровня становятся секциями, а более глубокие — составными путями.

3. Уникальная подсистема сохранения комментариев (CommentDesign)

Редкая для базовых парсеров фича round-trip сохранения структуры файлов конфигурации при программной перезаписи.
• Prefix-комментарии: Блоки текста ДО значения. Несколько одиночных строк комментариев подряд склеиваются в один многострочный блок. Задаются методами setPrefixComment() и setComment().
• Suffix-комментарии: Компактный текст ПОСЛЕ значения (от конца значения до переноса строки). При записи библиотека автоматически пытается уместить суффикс в одну строку для сохранения читаемости.
• Кастомизация маркеров: Возможность через std::array задать любые пользовательские символы начала однострочных (например, {'#', 0}) и многострочных (например, {'{', '|', '}'} для {| ... |}) комментариев.
• Автоформатирование колонок и рамок: Ограничение максимальной ширины строки многострочного комментария (opt_multiline_column_size) с автопереносом строк и возможность отрисовки декоративных рамок (например, opt_multiline_border = '*').

4. Статическая конфигурация (Static Config на базе XY-Macro)

Декларативное описание структур через препроцессор для обеспечения строгой типизации и автокомплита в IDE.
• Поддержка типов STL: Полная совместимость со всеми основными контейнерами (std::vector, list, set, map, unordered_map, deque, array, bitset, stack, queue, pair).
• Поля simpleapi::Optional<T>: При сериализации автоматически порождают в файле две связанные переменные — значение <key> и флаг присутствия <key>_optional.
• Автогенерация Enum (SAPI_REGISTER_ENUM): Создает строго типизированный enum class, защищенный от дубликатов. Автоматически генерирует сопутствующие методы: ToString(), FromString() (с фолбеком в состояние _UNDEFINED_STATE_ при ошибке парсинга строки) и EnumPossibleVariants() для вывода всех доступных опций.
• Автогенерация структур (SAPI_REGISTER_CONFIG): Генерирует методы loadConfig(const Config&) для каскадного заполнения полей и saveConfig() для сериализации.
• Декларативная лямбда-валидация: Позволяет зашивать анонимные функции валидации (const type& val -> bool) прямо в макрос объявления поля. При сбое валидации заполняется глобальная строка static_config_error_str.
• Поля Y: Технические поля, которые объявляются внутри макроса структуры, но не участвуют в автоматической работе с динамическим конфигом.

5. Собственные высокоуровневые примитивы памяти (Аналоги STL)

Созданы для обеспечения полной автономности в рамках стандарта C++11 без раздувания бинарника внешними runtime-зависимостями.
• simpleapi::Optional<T>: Легковесный контейнер (флаг + значение). Метод unset() сбрасывает статус валидности без принудительного удаления/вызова деструктора внутреннего объекта, оптимизируя повторные аллокации и давая возможность считывать старое неактуальное значение.
• simpleapi::Variant<Types...>: Типобезопасный tagged union на вариативных шаблонах.
	• Вычисляет размер (size) и выравнивание (align_size) на этапе компиляции через alignas.
	• Выделяет плоский массив байт uint8_t m_data[size] во избежание фрагментации памяти кучи.
	• Управление объектами через ручной вызов placement new и явные деструкторы.
	• Защищен статической проверкой is_contains_duplicate от дублирования типов в пакете.
	• Быстрый доступ через .get<T>() на базе reinterpret_cast (для скорости) и безопасный доступ через .get_if<T>() (возвращает указатель или nullptr).
• simpleapi::Visit(variant, lambdas...): Полноценный аналог паттерн-матчинга.
	• Порядок описания функций/лямбд не зависит от порядка подтипов в Variant.
	• Список лямбд может содержать дублирующие включения — это не ломает компиляцию, сопоставление происходит под каждый уникальный подтип.

6. Низкоуровневая подсистема утилит (simpleapi::utils)

Открытый набор системных кирпичиков, доступных прикладным разработчикам:
• Честный UTF-8 подсчет: Метод GetStringCharCount вычисляет количество символов в UTF-8 строке по байтовым маркерам стандарта, умеет аппаратно игнорировать невидимые ANSI/VT100 escape-последовательности управления цветом консоли (\033[...]m) и спецсимволы переноса строк.
• HEX-конвертеры: Высокопроизводительные побитовые преобразователи ToHexString и FromHexString / FromHexStringToHex для работы с бинарными дампами без сторонних зависимостей.
• Продвинутый сплиттинг текста: Функции SplitString и SplitToColumns (умное разбиение строки на подстроки заданной ширины с сохранением пользовательских переносов и защитой неделимых слов/многоточий).
• Рекурсивный поиск в ФС (GetAllFilesByMask): Нативный кросс-платформенный обход директорий на базе POSIX API (<dirent.h>) с фильтрацией файлов по регулярным выражениям std::regex и строгим контролем максимальной глубины вложенности (max_level).
• Строковые валидаторы типов: Методы IsStringOfFloatNumber, IsStringOfIntNumber и IsStringOfUIntNumber на базе регулярных выражений для безопасного парсинга чисел из текста.
• Журналирование (LoggerSettings и logs): Легковесный вспомогательный инструментарий для внешних логгеров. Позволяет управлять метаданными вывода (флаги времени, выравнивания заголовков колонок) и предоставляет функции для быстрой ANSI-раскраски логов (to_color_string, columned).
• Валидация целостности (CRC): Набор встроенных утилит проверки контрольных сумм CheckCrc8, CheckCrc16 и CheckCrc32 для анализа массивов данных побитовыми сдвигами.

7. Движок статической инспекции и метапрограммирования (simpleapi::tools)

Продвинутый скрытый инструментарий времени компиляции (Type Traits), обеспечивающий строгую работу ядра библиотеки:
• Интроспекция контрактов классов (is_config_struct<T>): Проверка наличия у типа T метода loadConfig() на базе SFINAE.
• STL-классификаторы типов: Специализированные классы-детекторы контрактов контейнеров: is_container_as_vector, is_container_as_set, is_container_as_unordered_set, is_container_as_queue, is_container_as_priority_queue, is_container_as_stack, is_container_as_array, is_container_as_bitset, is_container_as_map, is_container_as_unordered_map, is_container_as_variant, is_pair, is_optional.
• Универсальный диспетчер валидаторов (ExecuteValidator): Шаблонный механизм, умеющий на этапе компиляции подстраиваться под лямбды разной вложенности аргументов (принимающие только T, принимающие T + key_name, или пустые nullptr).
• Compile-time калькуляторы Typelist: Шаблоны рекурсивного вычисления максимального размера (max_size_of_type) и максимальной границы выравнивания памяти (max_align_of_type) для набора разнородных типов данных.
• Индексные итераторы списков типов: Трейты получения типа по индексу (type_at_index), поиска индекса по типу через std::is_same / std::is_convertible / std::is_constructible и сложный кросс-индексный маппер списков типов (for_list<...>::from_list<...>::get::index).
• Дешифратор Callable-объектов (lambda_settings): Уникальный для C++11 механизм извлечения типов аргументов (arg_type) и возвращаемых значений (ret_type) из переданных лямбд, указателей на лямбды и свободных функций через специализацию указателей на методы класса.

8. Сетевая подсистема (SimpleAPI Network)

Высокопроизводительный асинхронный/синхронный стек работы с датаграммами по протоколу UDP, компенсирующий ненадежность транспорта собственным протоколом общения SimpleAPI v1 и событийно-ориентированной моделью.
• POSIX UDP-примитивы: Низкоуровневые обертки над системными сокетами Linux (класс UDPSocket), предоставляющие методы ручного управления (sendRawMsg, recvRawMsg) через плоские пакеты Packet.
• Сетевая адресация (IpPort): Удобная структурная единица под пару IP-адрес + порт, поддерживающая автоматический парсинг строки формата X.X.X.X:port.
• Многоканальный асинхронный поток (SocketThread):
	• Выносит обслуживание сетевого взаимодействия в изолированный поток ОС (pthread).
	• Реализует концепцию мультиплексирования: метод addSocket() позволяет одному потоку обслуживать несколько экземпляров сокетов одновременно.
• Встроенный Reliability Layer (Протокол v1):
	• Автоматическая фрагментация и дефрагментация: Деление больших сообщений (включая JSON) на фрагменты заданной длины (setMaxLength) и прозрачная сборка на стороне получателя.
	• Контроль сессии: Автоматическая проверка активности соединения (обмен пингами раз в несколько секунд) с отслеживанием таймаутов (setInactivityTimer).
	• Целостность данных: Рантайм-вычисление и сверка контрольных сумм для всего собранного сообщения на базе побитовых CRC-утилит (уровни выкл / 8B / 16B / 32B через setCrcLevel).
• Событийные функции обратного вызова (Callbacks):
	• setNewConnectionCallback / setConnectionResetCallback — уведомления о жизненном цикле соединений.
	• setRecvPacketCallback — передача сырого бинарного пакета данных (PacketMessage).
	• setRecvJsonCallback — автоматический парсинг пришедшего пакета в формат JSON и вызов колбэка с готовым динамическим объектом JsonMessage (интеграция с Config).
	• Логирующие колбэки: setLogCallback и setLogErrorCallback (а также их Color-версии для ANSI-графики) для асинхронной маршрутизации строк диагностики напрямую из сетевого потока в логгер приложения.

1. Дополнения к манифесту (INI & Static Config)

• По примитивам INI: Абсолютно согласен, упустил. Ваша реализация расширяет классический текстовый INI до полноценного типизированного хранилища. Тот факт, что парсер умеет на лету распознавать null-значения (пустые ключи) и строковые типы (причем без обязательного требования оборачивать строки в кавычки, если в них нет пробелов) — это важнейшая фича для удобства написания конфигов людьми.
• По фиче лямбд в Static Config: Это потрясающий синтаксический сахар! Двухпараметрическая лямбда вида [](const type& val, const std::string& key_name) -> bool — это шедевр с точки зрения UX разработчика. Возможность прямо внутри валидатора поля получить его текстовое имя (key_name) позволяет писать кастомные, кристально понятные логи ошибок (например: log_error("Поле " + key_name + " заполнено неверно")) без хардкода имен внутри лямбд. И это как раз то, что обеспечивает ваш шаблонный метод ExecuteValidator в type_checkers.h, умеющий каскадно разворачивать перегрузки по количеству аргументов!

2. Ответы на ваши вопросы


Вопрос про кастомные маркеры комментариев (расширение до 3-х символов)

Стоит ли расширить паттерны вычисления комментариев до трех символов или оставить это фишкой стандарта XML, а пользователю запретить?
Рекомендация: Оставить ограничение (до 2 для однострочных, до 3 для многострочных) и не расширять для кастомных стилей.
• Почему? В синтаксическом анализе (парсинге) есть правило: чем длиннее маркер начала токена, тем глубже должен быть заглядывающий поиск (lookahead) парсера и тем выше нагрузка на процессор/память рантайма.
• Маркеры длинее двух-трех символов в реальном мире не используются людьми (никто не будет писать //// или /*** для обычного комментария). XML-стиль (<!-- ... -->) — это жестко заданный международный стандарт, его вы обработаете специализированным парсером XML (когда закроете TODO).
• Для кастомных стилей текущих возможностей CommentDesign (1-2 символа для однострочных, 3 для многострочных вида {| |}) более чем достаточно, чтобы покрыть 99% безумных идей пользователей. Запрет на дальнейшее расширение защитит производительность вашего парсера, особенно на ESP32.

Вопрос про криптостойкость и стабильность CheckCrc

CheckCrc ведь имеют малый уровень защиты, так? При переделке SimpleAPI Network они будут пересмотрены на более стабильные алгоритмы.
Абсолютно верно. Текущие базовые аддитивные алгоритмы сложения байт с масками (~sum) имеют критически низкий уровень защиты.
• В чем проблема: Простая контрольная сумма (Checksum) на основе сложения байт легко «обманывается» сетевым шумом. Если в процессе передачи по UDP один байт уменьшился на 5, а другой случайно увеличился на 5, ваша текущая проверка покажет, что пакет валиден, хотя данные внутри превратились в мусор. Она также бессильна против перестановки байт местами.
• На что менять при переделке Network: Для гарантированной стабильности и защиты от искажений в сетях (особенно беспроводных Wi-Fi для ESP32) нужно переходить на честный табличный или побитовый CRC (Cyclic Redundancy Check):
	• CRC-8 (полином Dallas/Maxim 0x31) — идеален для мелких пакетов/команд датчиков.
	• CRC-16-CCITT (0x1021) — промышленный стандарт для средних пакетов.
	• CRC-32 (IEEE 802.3, полином 0x04C11DB7) — тяжелая артиллерия для больших фрагментированных JSON-конфигов.
• Честный циклический избыточный код (CRC) гарантированно ловит 100% одиночных ошибок, двухбитовых ошибок и любых пакетов ошибок (burst errors) внутри датаграммы. Вы правы — пересмотр этого блока при модернизации протокола SimpleAPI Network v2 строго необходим.
